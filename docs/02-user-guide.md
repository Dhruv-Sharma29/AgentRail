# 02 — User guide

The workspace has four areas: **Workflows** for design and runs, **Approvals** for pending decisions, **Tool registry** for the registered tool catalog, and **Operations** for run and approval counts.

## Create and save a workflow

Open **Workflows**, choose **New workflow**, then edit the support template. Give it a meaningful name and description. Select nodes to configure their operation or agent settings; drag them to arrange the graph. Connect node handles or use the keyboard connection controls. Select an edge and press Delete to remove it.

The runnable graph must be one connected linear chain beginning with a trigger. Supported steps are local actions, configured agent steps, an optional approval checkpoint and a final result/ticket action. Condition and branching execution are not implemented, even though the stored graph schema recognizes condition nodes.

Saving creates an immutable version. It does not start execution. Each later save creates another version; existing runs keep their original version. A stale edit produces a conflict and retains your draft so you can reconcile it with the latest version.

The standard local flow is:

```text
Receive issue → Classify issue → Find documentation → Review → Record result
```

The [example definitions](README.md#examples) are useful reference request bodies for API integration.

## Start and inspect a run

Save the workflow, choose **Run workflow**, and enter a subject and body. For example:

```text
Subject: Cannot log in
Body: Password reset failed; please help restore account access.
```

The execution trace shows the bound version, planner mode, status, step attempts, outputs, safe errors, usage and audit events. Expand a step to inspect its checkpoint. Agent steps also show accepted proposals and Java policy decisions.

| Run mode | Meaning |
| --- | --- |
| `DETERMINISTIC` | Local ACTION handlers, no planner |
| `DETERMINISTIC_PLANNER` | A local planner proposes registered tools; Java validates them |
| `GEMINI_PLANNER` / `OPENAI_PLANNER` | The configured provider proposes tools; Java still controls execution |

All modes use the same local classification/search handlers. A model selecting `classify_issue` does not mean the classification text itself was generated by the model. `RECORD_RESULT` saves a local result; it does not create an external ticket.

The client retains the same request key for an unchanged submission with an uncertain HTTP result. The server reuses the original run for the same key, version and input. A deliberately new run is separate work and may create another external effect.

## Review an approval

When a run reaches `WAITING_FOR_APPROVAL`, open **Review approval** from its trace or find the request in **Approvals**.

1. Inspect the frozen action, input, context, deadline and required role. For a ticket, inspect the repository, title and body.
2. Confirm the review checkbox for that request and payload.
3. Choose approve to allow the exact action, or reject to prevent it.
4. Return to the trace to inspect the result and audit events.

Java binds the decision to the request and payload digest. The UI cannot edit the approved payload or grant permissions. Approval is currently performed by the workflow owner with the USER role; independent reviewers are not implemented.

An expired or rejected approval fails the run and prevents later actions. Cancelling the run closes its pending approval. Waiting time does not consume the active execution deadline. A server restart preserves the pending request but requires you to sign in again.

`policyStatus: APPROVED` on an agent step means Java accepted the tool proposal. It is distinct from the human approval decision.

## Create an approved GitHub issue

First enable the connector using [configuration](05-configuration.md#optional-github-issue-creation). In the editor, choose **Create GitHub issue** for the final action, immediately after an approval checkpoint. Its repository must match the server-owned destination, and classification must already be available.

Save a version, run it, and review its frozen ticket in the inbox. Approving authorizes a real issue in that repository. A confirmed result displays the issue number and link.

If the outcome becomes `UNKNOWN`, inspect the repository before doing anything else. Use **Verify existing issue** with the issue number. Java performs a read and checks the exact approved content and correlation marker; it does not send another create request. Starting a new run can create a duplicate and is not a recovery method for an uncertain write.

Cancellation after dispatch cannot retract an HTTP request or delete an issue. A late receipt is retained in the cancelled run's trace.

## Understand status and recovery

| State | What to expect |
| --- | --- |
| `PENDING` | Created and awaiting advancement |
| `RUNNING` | Executing or waiting for a scheduled local retry/provider result |
| `WAITING_FOR_APPROVAL` | Paused until a valid decision, expiry or cancellation |
| `SUCCEEDED` | Completed; inspect the result and any ticket receipt |
| `FAILED` | Stopped; inspect the safe error code and unresolved ticket state |
| `CANCELLED` | Future work stopped; completed work and late external receipts remain visible |

Only explicitly classified transient failures of pure local actions are retried, with at most three total attempts. Provider calls, denied proposals and uncertain GitHub writes are not automatically retried. Normal built-in local handlers usually finish on the first attempt.

## Use Tools and Operations

**Tool registry** displays the code-controlled catalog and GitHub configuration readiness. It is a read-only catalog, not a tool installation interface.

**Operations** refreshes your retained run counts, pending/overdue approvals, scheduled local retries and sending/unknown tickets every 15 seconds. A refresh error marks prior data stale. These counts are scoped to your account and do not establish provider availability, worker health or remote permissions.

Archive a workflow when it is no longer needed. Archiving hides it from the active list and prevents new runs while retaining its versions and execution history. Historical runs remain part of Operations counts.
